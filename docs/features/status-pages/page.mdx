# Status Pages

A status page shows your users whether your services are up, without giving them access to Temps. You pick which uptime monitors appear and what they are called; Temps publishes their current state, 90 days of daily uptime and the incident updates you mark as public, at an unguessable link. {{ className: 'lead' }}

Status pages are **Beta**. See [feature maturity](/docs/feature-maturity).

---

## What a visitor sees

- A banner with the overall state: all operational, degraded, or down.
- One row per selected monitor, under the **public name** you gave it, with its current state, uptime over 90 days and a bar per day.
- Active and recently resolved (last 14 days) incidents, showing only the updates you made public.

The page is plain HTML with no JavaScript and refreshes itself every minute. The same data is available as JSON at `…/summary.json` for widgets and scripts.

### What is never published

A status page is built from an allowlist, not by hiding fields from the internal view. It never contains:

- monitor names, URLs, check paths, hostnames or IP addresses;
- probe response bodies or error messages;
- project or environment names;
- database IDs of any kind;
- incident titles and descriptions (an incident's heading is derived from its severity, e.g. "Partial outage");
- incident updates you did not make public;
- anything about monitors you did not select, or incidents tied only to them.

## Create and publish a page

1. Open the project and go to **Observe → Status Pages** (also linked from the **Uptime** page).
2. Click **Create status page** and give it a public title. The page starts as a **draft**: its link returns "not found".
3. Under **Monitors**, tick each monitor to show and type its **public name**, for example `API` or `Dashboard`. Internal names are never pre-filled as public names. Click **Save changes**.
4. Click **Publish**. The **Public link** is now live; copy it and share it.

Publishing needs at least one selected monitor.

### From the CLI

```bash
# Create a draft showing monitor 12 as "API" and monitor 15 as "Dashboard"
temps status-pages create --project-id 3 --title "Acme status" \
  --monitor 12=API --monitor 15=Dashboard

temps status-pages publish --id 1
temps status-pages show --id 1        # prints the public URL
```

### From the API

| Action | Endpoint |
|---|---|
| List a project's pages | `GET /api/projects/{project_id}/status-pages` |
| Create a draft | `POST /api/projects/{project_id}/status-pages` |
| Read one | `GET /api/status-pages/{id}` |
| Change title, description or monitors | `PATCH /api/status-pages/{id}` |
| Publish / unpublish | `POST /api/status-pages/{id}/publish`, `POST /api/status-pages/{id}/unpublish` |
| Replace the public link | `POST /api/status-pages/{id}/rotate-url` |
| Delete | `DELETE /api/status-pages/{id}` |

The public view is served without authentication at `GET /api/status/{slug}` (HTML) and `GET /api/status/{slug}/summary.json` (JSON).

## Taking a page down

Each of these makes the old link return "not found" **immediately**, before the API call returns:

- **Unpublish** keeps the page and its settings as a draft.
- **Replace public link** issues a new link and retires the old one, for when a link was shared too widely.
- **Delete** removes the page. Deleting the project takes all its pages down; deleting a selected monitor removes it from the page.

Public responses are sent with `Cache-Control: no-store`, so browsers and proxies do not keep a copy after you take the page down.

## Public incident updates

Incident updates are **private by default**. To share one:

- In the console, open a status page and use **Incident updates**: switch an existing update to **Public**, or post a new update with **Show on status pages** ticked.
- From the CLI: `temps incidents update-status --id 7 --status identified --message "…" --public`, or `temps incidents set-visibility --id 7 --update-id 31 --public`.

The automatic first update ("Incident created: …") contains the internal incident title and can never be made public.

An incident appears on a page when it has at least one public update and it concerns a monitor selected on that page, an environment one of those monitors watches, or the whole project.

## Permissions and audit

Creating a page needs `status_page:create`; changing it, publishing, unpublishing, replacing its link or changing an incident update's visibility need `status_page:write`; deleting needs `status_page:delete`. On projects with team access these start at the project **admin** role, so viewers and deployers cannot publish anything.

Every change is written to the audit log (`STATUS_PAGE_CREATED`, `STATUS_PAGE_UPDATED`, `STATUS_PAGE_PUBLISHED`, `STATUS_PAGE_UNPUBLISHED`, `STATUS_PAGE_URL_ROTATED`, `STATUS_PAGE_DELETED`, `STATUS_PAGE_INCIDENT_UPDATE_VISIBILITY_CHANGED`), including the exact list of monitors selected when the selection changes.

## How it is served

- Public requests are answered from an in-memory snapshot. They never run a probe or a database query, so traffic to a status page — including someone guessing links — cannot slow Temps down.
- Snapshots are rebuilt every minute, and immediately when you change or publish a page or an incident update's visibility.
- The link contains 128 random bits; it cannot be guessed or derived from any ID. Unknown, unpublished, deleted and replaced links all receive the same "not found" response.
- Requests are rate-limited per client (300 per minute per IPv4 address or IPv6 /64). Visitors that cannot be tracked individually during a flood share a separate budget, so a flood of addresses cannot lock out visitors already being served.
- The page asks search engines not to index it (`noindex`), so the link stays as private as you keep it.
- Pages are served on Temps' public-only routes (the same surface as webhook receivers), so they keep working when the console itself is restricted to an IP allowlist. The link uses your public ingress URL when one is configured, otherwise the external URL.

## Limits

- 10 status pages per project, 50 monitors per page.
- Titles up to 120 characters, descriptions up to 1,000, public names up to 80, incident update messages up to 5,000.
- Custom domains for status pages are not supported yet; pages are served under your Temps public URL.
