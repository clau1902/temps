## Sentry Compatibility {{ anchor: true, id: 'sentry-compatibility' }}

Temps adapts supported Sentry SDK ingestion payloads to the existing Temps data model and services. Browse and manage the results through Temps APIs and console pages. This does not provide Sentry's issue, organization, alert-rule, or other management APIs.

### Verified SDK contract

Compatibility is defined by SDK version and scenario, rather than a percentage:

| Official SDK | Pinned upstream source | Verified scenarios |
| --- | --- | --- |
| `@sentry/node@10.17.0` | [eb6e2946](https://github.com/getsentry/sentry-javascript/tree/eb6e2946eb45583dd4c02ec92f8912e5bad51943) | Exceptions, messages, structured logs, transaction spans, check-ins; direct and DSN-authenticated tunnel ingestion |
| `@sentry/node@11.8.0` | [c6492ef7](https://github.com/getsentry/sentry-javascript/tree/c6492ef78c7bfb97931e43075763ce84ee8fda7e) | Errors, logs, streamed spans, counter/gauge/distribution metrics, check-ins, mixed envelopes and trace linkage |
| `@sentry/browser@11.8.0` in Chromium | [c6492ef7](https://github.com/getsentry/sentry-javascript/tree/c6492ef78c7bfb97931e43075763ce84ee8fda7e) | Logs, spans, metrics, compressed and plain web replay; direct and DSN-authenticated tunnel ingestion; desktop and phone viewport playback |

These checks use synthetic applications, real HTTP endpoints, native storage queries and console inspection. They do not establish compatibility with every integration in these SDKs, other SDK versions, React Native, Cocoa, Android, native binaries, or a customer's production application. Node 10.17.0 supplies log trace IDs in the verified scenario but omits the active parent span attribute; Node 11.8.0 supplies both.

### Signal and product coverage

“Adapted” means ingestion feeds an existing native service. “Native extension” identifies additional Temps behavior. “Outstanding” means there is no verified compatibility contract for that capability.

| Area | Contract and native destination | Limits or outstanding work |
| --- | --- | --- |
| DSN and transport | Adapted: project-scoped public DSNs, gzip, byte-length envelope framing, mixed items and authenticated tunnels | Public DSNs are write-only. OTLP and management endpoints still require server authentication. |
| Errors, messages and stacks | Adapted: native error events, groups and stack details | Symbolication depends on available native source artifacts; native crash decoding is separate. |
| Breadcrumbs, users, tags and contexts | Adapted: error detail payload and native metadata | Not every context field becomes a separately indexed native column. |
| Fingerprints and grouping | Adapted: native fingerprints and grouping; concurrent insertion and counts reconciled | Sentry grouping algorithm parity and grouping configuration APIs are not provided. |
| Issue APIs and triage | Existing native error list, detail and resolution APIs/UI | Sentry issue APIs are not implemented. |
| Alert APIs and alerts | Existing Temps alert rules and alarms; cron health feeds native alarms | Sentry alert APIs are not implemented. Delivery requires a configured provider; external delivery was not verified in the synthetic run. |
| Debug ID source maps and artifact bundles | Existing native release/source-map path remains available | Modern Debug ID artifact-bundle ingestion and resolution are outstanding. |
| Releases | Adapted: release identity on errors, logs, spans, metrics and check-ins | A release label does not create a Sentry release-management API, deploy history, or release-health dashboard. |
| Tracing | Adapted: transaction events and version-2 batched span items become native spans | Other span versions and Sentry performance product parity are outstanding. |
| Structured logs | Adapted: version-1/2 batched `log` items become native telemetry logs | Typed attributes are preserved as source metadata; native attribute search remains string-based. |
| Metrics | Adapted: version-1/2 batched `trace_metric` items become native metric points | Counters are delta monotonic sums; each distribution observation is a delta histogram. Legacy StatsD, cumulative inputs and future versions are unsupported. |
| Replay | Adapted: paired web replay metadata and rrweb recording segments become native visitors and replays | No Temps analytics SDK required. Mobile/video replay is unsupported; technical custom events still have generic timeline labels. |
| Cron monitoring | Native extension: SDK check-ins, interval/crontab schedules, missed-run and timeout detection, native management and run history | Temps observes the existing scheduler; it does not execute jobs. See [Cron monitoring](/docs/monitoring#cron-monitoring). |
| Release health | Outstanding | Session/aggregate-session payloads, crash-free rates and adoption need separate product work. |
| Profiles | Outstanding | Profiling payloads, storage, aggregation and flamegraphs need separate product work. |
| Feedback | Outstanding | No verified Sentry feedback ingestion contract. |
| Attachments | Outstanding | Binary framing is supported; attachment storage and attachment APIs are not. |
| Minidumps and native crashes | Outstanding | Native crash parsing, symbols and processing need separate product work. |
| CSP and NEL reports | Outstanding | No verified security-report or network-error-report ingestion contract. |
| Client outcomes | Outstanding | Client reports are counted as unsupported; they do not populate native outcomes analytics. |

### Framing, failures and fidelity

The envelope reader handles explicit byte lengths, implicit newline termination, EOF, empty bodies, binary content and multiline payloads. Unknown item types are skipped within the same size/count limits and reported through bounded `x-temps-sentry-unsupported-items` and `x-temps-sentry-unsupported-types` response headers. Skipped items are never counted as stored. A successful envelope response alone does not establish signal support.

The HTTP body limit remains 2 MiB compressed and 10 MiB decompressed. Envelope and item headers are limited to 8 KiB, with at most 1,000 items. Telemetry batches are bounded to 1,000 records and 128 attributes per record. Each envelope accepts at most one log batch, one metric batch, 100 check-ins, and one paired replay segment. Span items can combine up to 1,000 spans in total. Repeated log/metric batches or replay segment pairs are rejected even when their framing is valid. Native quotas, ingest permits, retention, cloud routing and consent apply. Replay decoding has its own bounded segment/session limits.

Supported items are decoded and validated before writes. Storage then proceeds through native domain services, without a cross-domain transaction. Receipt headers such as `x-temps-sentry-logs-stored`, `x-temps-sentry-spans-stored`, `x-temps-sentry-metrics-stored` and `x-temps-sentry-check-ins-stored` report confirmed progress. Capacity/quota failures return 429; transient telemetry storage failures return 503 with `Retry-After`; permanent failures are not acknowledged as success. Retrying a partially stored mixed envelope can duplicate errors, logs, spans or metric observations. Check-in IDs and replay segment identities provide their own bounded deduplication; there is no envelope-wide exactly-once guarantee.

Native log attributes are strings. The reserved `temps.sentry.attributes` JSON attribute preserves original declared types and numeric text; `temps.sentry.timestamp` and `temps.sentry.severity_number` preserve timestamp and severity fidelity. Template arguments, release/environment metadata and trace/span linkage remain available through native records. Database timestamps may resolve to microseconds, and native metric aggregation uses floating-point values; preserved source text does not make native numeric queries exact for every integer or decimal.

Version-2 automatic IP/user-agent inference is unsupported. For the verified JavaScript 11.8.0 setup, use `dataCollection: { userInfo: false }`. This is distinct from choosing which explicitly supplied user fields to send. SDKs can still emit other unsupported items by default; disable unused features such as client reports where appropriate.

The wire baselines are the official [envelope](https://develop.sentry.dev/sdk/foundations/envelopes/), [structured log](https://develop.sentry.dev/sdk/telemetry/logs/) and [metric](https://develop.sentry.dev/sdk/telemetry/metrics/) specifications, interpreted against the pinned SDK revisions above.

## Setup & Integration {{ anchor: true, id: 'setup' }}

Get started with error tracking in minutes using your existing Sentry SDK.

### Step 1: Get Your DSN

Each project gets a unique DSN (Data Source Name) for error reporting. The DSN format is:

```
https://<public_key>@<temps_app>/<project_id>
```

**Example DSN format:**
```
https://742ee692155dd1cb2cecd94838bb425d4b5a1184e5b57c0815e9d808a6f8d70d@your-temps-instance.com/1
```

### Get Your DSN

Visit your project's error tracking setup page to view and copy your unique DSN:

```
https://<temps_app>/projects/<project_slug>/errors?tab=setup
```

**Example:**
```
https://app.temps.davidviejo.dev/projects/my-app/errors?tab=setup
```

On this page, you'll find:
- **Your project's unique DSN** - Copy this to use in your Sentry SDK configuration
- Setup instructions for different platforms
- Environment-specific DSNs (if configured)
- Rate limits and configuration options

<Note>
**Important:** Each project has a unique DSN. You must copy your actual DSN from the setup page—the DSN shown in examples above is just a format reference. Your DSN will have a different public key.

**DSN Format:** The DSN consists of:
- **Public Key**: A 64-character hexadecimal string (unique per project)
- **Temps App URL**: Your Temps instance URL
- **Project ID**: Numeric project identifier

The DSN is automatically generated when you first visit the setup page.
</Note>

### Step 2: Install Sentry SDK

Install the official Sentry SDK for your platform:

<CodeGroup>
```bash {{ title: 'JavaScript/React' }}
npm install @sentry/react
```

```bash {{ title: 'Next.js' }}
npm install @sentry/nextjs
```

```bash {{ title: 'Node.js' }}
npm install @sentry/node
```

```bash {{ title: 'Python' }}
pip install sentry-sdk
```

```bash {{ title: 'Go' }}
go get github.com/getsentry/sentry-go
```
</CodeGroup>

### Step 3: Configure SDK

Point the Sentry SDK to your Temps instance:

<CodeGroup title="Configure Sentry SDK">
```typescript {{ title: 'React' }}
import * as Sentry from '@sentry/react';

Sentry.init({
  // Copy your DSN from: https://<temps_app>/projects/<project_slug>/errors?tab=setup
  dsn: process.env.NEXT_PUBLIC_SENTRY_DSN || 'YOUR_DSN_HERE',
  environment: 'production',
  release: 'my-app@1.0.0',

  // Performance monitoring
  tracesSampleRate: 1.0,

  // Session replay integration
  integrations: [new Sentry.BrowserTracing()],

  beforeSend(event, hint) {
    // Filter sensitive data
    return event;
  }
});
```

```typescript {{ title: 'Next.js' }}
// sentry.client.config.ts
import * as Sentry from '@sentry/nextjs';

Sentry.init({
  dsn: process.env.NEXT_PUBLIC_SENTRY_DSN,
  environment: process.env.NODE_ENV,
  tracesSampleRate: 1.0,
  replaysSessionSampleRate: 0.1,
  replaysOnErrorSampleRate: 1.0,
});
```

```python {{ title: 'Python' }}
import sentry_sdk
import os

# Copy your DSN from: https://<temps_app>/projects/<project_slug>/errors?tab=setup
sentry_sdk.init(
    dsn=os.getenv("SENTRY_DSN", "YOUR_DSN_HERE"),
    environment="production",
    release="my-app@1.0.0",
    traces_sample_rate=1.0,
)
```

```go {{ title: 'Go' }}
package main

import (
    "github.com/getsentry/sentry-go"
    "os"
)

func main() {
    // Copy your DSN from: https://<temps_app>/projects/<project_slug>/errors?tab=setup
    dsn := os.Getenv("SENTRY_DSN")
    if dsn == "" {
        dsn = "YOUR_DSN_HERE"
    }

    err := sentry.Init(sentry.ClientOptions{
        Dsn: dsn,
        Environment: "production",
        Release: "my-app@1.0.0",
        TracesSampleRate: 1.0,
    })
    if err != nil {
        log.Fatalf("sentry.Init: %s", err)
    }
    defer sentry.Flush(2 * time.Second)
}
```
</CodeGroup>

## Error Grouping {{ anchor: true, id: 'error-grouping' }}

Temps automatically groups similar errors together using smart fingerprinting and AI-powered clustering.

### Grouping Strategies

<Properties>
  <Property name="Stack Trace Fingerprinting">
    Groups errors with identical stack traces (default)
  </Property>
  <Property name="Exception Type">
    Groups by exception class/type (TypeError, ReferenceError, etc.)
  </Property>
  <Property name="Error Message">
    Groups by error message pattern (parameterized)
  </Property>
  <Property name="AI Clustering">
    Uses OpenAI embeddings to find semantically similar errors
  </Property>
  <Property name="Custom Fingerprinting">
    Define custom grouping rules via fingerprint tags
  </Property>
</Properties>

### Custom Fingerprinting

Override default grouping with custom fingerprints:

<CodeGroup title="Custom Fingerprinting">
```typescript {{ title: 'JavaScript' }}
Sentry.captureException(error, {
  fingerprint: ['database-error', 'connection-timeout'],
});

// Dynamic fingerprint
Sentry.captureException(error, {
  fingerprint: ['api-error', error.response?.status],
});
```

```python {{ title: 'Python' }}
with sentry_sdk.configure_scope() as scope:
    scope.fingerprint = ['database-error', 'connection-timeout']
    sentry_sdk.capture_exception(error)
```
</CodeGroup>

### Merge & Split Groups

Groups cannot be merged or split after the fact. To change how future events group, send a [custom fingerprint](#custom-fingerprinting) from your SDK: events with the same fingerprint land in one group, and events with different fingerprints are kept apart.

### Source Context (see the code) {{ anchor: true, id: 'source-context' }}

Temps can show the actual source code around each stack frame, not just
`file:line`. How the source gets there depends on the language:

- **JavaScript / TypeScript** — upload **source maps**. The original source
  travels inside the `.map` (`sourcesContent`), so minified production frames
  resolve to readable code automatically. The official Sentry build plugins and
  `sentry-cli` upload to Temps unchanged (Temps injects `SENTRY_URL` /
  `SENTRY_AUTH_TOKEN` for git-based deploys).

- **Go, Rust, Python, and other native languages** — these already report the
  *original* `file:line`, they just don't ship the source. Upload the raw
  source per release and Temps renders the code around each frame.

  Native source context is **opt-in per project** (Settings → General → *Error
  Tracking Source Context*) — application source is only stored when you enable
  it.

For **git-based deploys**, that's all you need: once the toggle is on, Temps
captures the source automatically after each deploy, keyed by the commit SHA.
By default it captures from the **Docker build context** — the exact directory
the image was built from — which is the right root for Dockerfile deploys and
monorepos (frame paths are relative to what was copied into the build). To
narrow or override it:

```yaml {{ title: '.temps.yaml' }}
sourceContext:
  root: services/api    # capture from here (relative to the repo); default: build context
  include: [go, rs]     # override the default source-extension set
```

...or set the **Source Root** in the project's error-tracking settings. For
**image deploys / external CI**, upload the source yourself (below).

The release you upload under **must match the SDK's reported release**
(`SENTRY_RELEASE`) — typically the deployed commit SHA or tag. For image-based
deploys Temps injects `SENTRY_RELEASE` from the deployed image tag/digest, so
key your upload the same way.

<CodeGroup title="Upload source in CI (native)">
```bash {{ title: 'Whole tree' }}
# Upload every source file under the repo, keyed by the release.
# file_path is each file's path relative to the root — exactly how a
# -trimpath Go binary (and most native SDKs) report frame filenames.
bunx @temps-sdk/cli errors source-files upload \
  --project-id 42 \
  --release "$CI_COMMIT_SHA" \
  --dir .
```

```bash {{ title: 'Single file' }}
bunx @temps-sdk/cli errors source-files upload \
  --project-id 42 \
  --release "$CI_COMMIT_SHA" \
  --file internal/gateway/middleware.go \
  --file-path internal/gateway/middleware.go
```

```bash {{ title: 'List / delete' }}
bunx @temps-sdk/cli errors source-files list   --project-id 42 --release "$CI_COMMIT_SHA"
bunx @temps-sdk/cli errors source-files delete --project-id 42 --release "$CI_COMMIT_SHA"
```
</CodeGroup>

<Note>
  **Compiled services (Go, Rust, …): don't hard-code the release.** Some SDKs
  let you set the release in code (e.g. `sentry.ClientOptions{ Release: version }`).
  If you bake a placeholder like `"dev"` into the binary, the SDK will **ignore**
  the `SENTRY_RELEASE` Temps injects at deploy time, and your events won't line up
  with the source you uploaded. Either:

  - leave the release **unset** in code so the injected `SENTRY_RELEASE` wins, or
  - bake the **real** commit/tag at build time, e.g. Go
    `-ldflags "-X main.version=$VERSION"` with
    `VERSION="${CI_COMMIT_TAG:-$CI_COMMIT_SHA}"` (and pass the same value as the
    `--release` you upload source under).
</Note>

## Error Resolution {{ anchor: true, id: 'resolution' }}

Manage error lifecycle from discovery to resolution.

### Error States

<Properties>
  <Property name="Unresolved">
    New or ongoing errors (default state)
  </Property>
  <Property name="Resolved">
    Marked as fixed (manually or automatically)
  </Property>
  <Property name="Ignored">
    Known errors that should be suppressed
  </Property>
  <Property name="Regressed">
    Error recurred after being resolved
  </Property>
</Properties>

### Mark as Resolved

<CodeGroup title="Resolve Errors">
```bash {{ title: 'CLI' }}
# Find the group ID (numeric) of an unresolved error
temps errors list --project-id 42 --status unresolved

# Resolve one error group
temps errors update --project-id 42 --group-id 123 --status resolved

# Reopen it
temps errors update --project-id 42 --group-id 123 --status unresolved
```

```typescript {{ title: 'API' }}
// Resolve error group 123 in project 42
await fetch('https://your-temps-instance.com/api/projects/42/error-groups/123', {
  method: 'PUT',
  headers: {
    'Authorization': `Bearer ${API_KEY}`,
    'Content-Type': 'application/json'
  },
  body: JSON.stringify({ status: 'resolved' })
});
```
</CodeGroup>

The CLI and API change one group at a time; to resolve several, run the command once per group ID.

### Auto-Resolution

Configure automatic resolution rules:

```yaml
# Auto-resolve errors
auto_resolution:
  # Resolve if no new events for X days
  no_events_for: 30

  # Resolve when new release is deployed
  on_release: true

  # Resolve when error rate drops below threshold
  rate_threshold:
    errors_per_hour: 1
    duration: 24h
```

### Ignore Errors

Suppress known errors you don't want to track:

<CodeGroup title="Ignore Errors">
```typescript {{ title: 'Client-Side' }}
Sentry.init({
  dsn: '...',
  ignoreErrors: [
    // Ignore specific error messages
    'ResizeObserver loop limit exceeded',
    'Non-Error promise rejection',

    // Ignore error patterns
    /^Loading chunk [\d]+ failed$/,
  ],

  // Ignore errors from specific URLs
  denyUrls: [
    /extensions\//i,
    /^chrome:\/\//i,
  ],

  beforeSend(event, hint) {
    // Custom ignore logic
    if (event.exception) {
      const error = hint.originalException;
      if (error.message?.includes('Network error')) {
        return null; // Don't send to Temps
      }
    }
    return event;
  }
});
```

```bash {{ title: 'CLI' }}
# Ignore one error group
temps errors update --project-id 42 --group-id 123 --status ignored
```
</CodeGroup>

Ignoring by message pattern is done in the SDK with `ignoreErrors`, as shown above; the server has no pattern rules.
