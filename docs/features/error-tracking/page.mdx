## Sentry Compatibility {{ anchor: true, id: 'sentry-compatibility' }}

Temps adapts supported Sentry SDK ingestion payloads to the existing Temps data model and services. Browse and manage the results through Temps APIs and console pages. This does not provide Sentry's issue, organization, alert-rule, or other management APIs.

The source-map contract pins [`sentry-cli@3.8.0`](https://github.com/getsentry/sentry-cli/tree/b602219e19ba29562996597a4d01b4a3bec4e7fc), its SYSB v2 artifact format (symbolic-debuginfo 13.8.0), Node SDK 11.8.0 and an esbuild 0.25.10 synthetic build. `scripts/sentry-protocol-conformance.py` checks CLI injection/upload/reupload, release-independent late symbolication, actual SDK discard reports, browser CSP and native NEL logs. Public DSNs cannot upload or read source artifacts; use a full-access project deployment token kept in build secrets. **Errors → Source maps** exposes artifact management and build credentials.

Live acceptance pins Playwright 1.64.1 and full Chromium 156.0.8078.4 (`channel: 'chromium'`). It verifies an actual CSP violation through native issue details and automatic NEL reporting of a synthetic HTTP 503 through a temporary local TLS forwarding endpoint into native logs. The test requires delivery and checks the stored URL, status, method, phase, severity and release; an explicit W3C DNS-error fixture additionally checks typed native log fields. Playwright's separate default headless shell produced no NEL reports in the same scenario. The test certificate is accepted only by its temporary SPKI pin, without modifying the machine's trust store.

Client-outcome acceptance checks actual SDK `beforeSend`/`beforeSendLog` discards and two independent official clients reporting the same discard quantities without identities. Additional wire fixtures verify that identical unidentified reports both count, 12 concurrent identified retries increment once, independent event IDs and repeated item positions remain distinct, and updated report bytes are accepted. Native HTTP tests force transaction aborts and mixed-envelope partial failures to verify receipt rollback and retry behavior. Byte-count coverage uses the official client's `recordDroppedEvent` API to simulate a buffer overflow, because the pinned SDK did not emit byte outcomes automatically in that scenario.

The [Sentry client-report protocol](https://develop.sentry.dev/sdk/telemetry/client-reports/) explicitly defines totals as approximate: reports may be lost and have no required stable ID. Temps suppresses exact retries for 24 hours when an envelope supplies a nonzero `event_id`: the receipt matches the authenticated project/environment/deployment, event ID, item position and exact report bytes. Different event IDs, repeated report items at different positions and changed report bytes remain independent. Standalone reports without an event ID always count, so their retries and lost reports can still affect totals. No SDK extension is required; the pinned Node SDK sends its standalone reports without an event identity, so those remain approximate.

`x-temps-sentry-client-outcomes-accepted` counts newly incorporated discard entries, and `x-temps-sentry-client-outcomes-duplicates` counts entries suppressed as identified retries; neither header is the discarded-event quantity. Receipt claims and counters use one bulk SQL statement per envelope, with at most 1,000 entries/receipt keys and no per-discard database operations. This handles periodic SDK health batches (for example, one batch per client per minute), independently of proxy request volume. Receipts retain hashes only for 24 hours.

Atomic hourly budgets admit at most 32,768 identified reports per project and 131,072 across the installation; duplicates and unidentified reports consume no receipt budget. At saturation a new identified report returns HTTP 503 with `Retry-After: 60`, and the entire report batch rolls back. Existing acknowledged duplicates still succeed. The 24-hour window therefore covers at most 25 hourly admission buckets; indexed cleanup removes expired receipt/budget rows in batches of 2,000. Existing admission permits, DSN limits and database backpressure also apply. A failed statement rolls back receipts and counters together; a later mixed-envelope failure can return confirmed outcome counts before retrying the remaining signals.

These checks use synthetic applications, real HTTP endpoints, native storage queries and console inspection. They do not establish compatibility with every integration in these SDKs, other SDK versions, React Native, Cocoa, Android, native crash payloads, or a customer's production application. Node 10.17.0 supplies log trace IDs in the verified scenario but omits the active parent span attribute; Node 11.8.0 supplies both.

### Framing, failures and fidelity

The envelope reader handles explicit byte lengths, implicit newline termination, EOF, empty bodies, binary content and multiline payloads. Unknown item types are skipped within the same size/count limits and reported through bounded `x-temps-sentry-unsupported-items` and `x-temps-sentry-unsupported-types` response headers. Skipped items are never counted as stored. A successful envelope response alone does not establish signal support.

The HTTP body limit remains 2 MiB compressed and 10 MiB decompressed. Envelope and item headers are limited to 8 KiB, with at most 1,000 items. Telemetry batches are bounded to 1,000 records and 128 attributes per record. Repeated log and metric batches may be interleaved; their combined totals must stay within 1,000 logs and 1,000 metric points per envelope. Each envelope accepts at most 100 check-ins and one paired replay segment. Span items can combine up to 1,000 spans in total. Repeated replay segment pairs are rejected even when their framing is valid. Native quotas, ingest permits, retention, cloud routing and consent apply. Replay decoding has its own bounded segment/session limits.

The original error JSON is retained alongside native metadata; envelope event IDs are canonicalized according to envelope-header precedence. Error stacks may come from exceptions, a top-level stack, or a matching/unique current thread. Ambiguous threads are not guessed. The console reads both dictionary and legacy pair-list headers/tags, and both breadcrumb wire forms.

Supported items are decoded and validated before writes. Storage then proceeds through native domain services, without a cross-domain transaction. Receipt headers such as `x-temps-sentry-logs-stored`, `x-temps-sentry-spans-stored`, `x-temps-sentry-metrics-stored` and `x-temps-sentry-check-ins-stored` report confirmed progress. Rate/quota failures return 429; shared ingest-capacity exhaustion and transient telemetry storage failures return 503 with `Retry-After`; permanent failures are not acknowledged as success. SDK error event IDs are deduplicated per project for seven days after native ingestion, atomically with the error row and group count. A retry returns zero new errors and an `x-temps-sentry-errors-duplicates` receipt; it does not reopen the group or fire another alert. Reusing an ID with a conflicting authenticated environment/deployment is rejected. On native TimescaleDB storage, spans use authenticated-scope trace/span identities; log and metric observations use an envelope event ID, item position, exact item bytes and record position when that identity exists. Claims, native rows and trace summaries commit together. Identified retries add zero new rows for one hour, including retries after partial ingestion or a lost response. Anonymous observations remain independent; content equality or a sequence number alone is not a safe client identity. Native OTLP, Cloud-primary outboxes and best-effort archive delivery retain their existing delivery semantics; this is not an envelope-wide or cross-backend exactly-once guarantee. Check-in IDs and replay segment identities provide their own bounded deduplication.

Retry receipts retain hashes only. Hourly admission allows 16,384 new identities per project and 65,536 per installation; the one-hour window spans at most two admission buckets. At capacity, new identified batches return 503 with `Retry-After: 60`, atomically rolling back their receipts and rows. Existing duplicates and fully anonymous batches remain admissible under the normal DSN, quota and concurrency limits. Indexed cleanup deletes at most 2,000 expired receipts and budget rows per 15-second pass. Ingestion performs one batch claim per signal transaction, never one database call per log or metric.

Native log values retain their exact string representation, with a separate native `attribute_types` map for SDK and OTLP declared types. The reserved `temps.sentry.attributes` JSON attribute also preserves original SDK types and numeric text; `temps.sentry.timestamp` and `temps.sentry.severity_number` preserve timestamp and severity fidelity. Template arguments, release/environment metadata and trace/span linkage remain available through native records. Native log integer and numeric filters use precision-preserving database comparisons. Database timestamps may resolve to microseconds, and native metric aggregation uses floating-point values; preserved metric source text does not make metric arithmetic exact for every integer or decimal.

The Rust `priority_sdk_cross_runtime_traces_and_typed_logs` test sends official Python 2.42.1 logs through the DSN endpoint, then checks native types, exact int64/range filtering, boolean/string distinctions, release and trace links, invalid filters and write-only DSNs. Browser acceptance exercises the same filter form and native rows at desktop and phone sizes. The same Rust test checks actual Python 2.42.1, Go 0.36.2 and Rust 0.41.0 root/child spans, parent IDs, status, kind, attributes and resources through native trace queries. Python child statuses serialized as `tags.status` are adapted with explicit top-level status taking precedence.

Native log queries accept paired `attribute_key`/`attribute_value`, optional `attribute_type` and `attribute_op` (`eq`, `ne`, `lt`, `lte`, `gt`, `gte`). Range comparisons require integer or double types; integer inputs must fit signed int64 and numeric inputs must be finite. The console exposes these controls under **Logs → Telemetry logs**. Numeric inputs stay text throughout the client and service to avoid JavaScript rounding. Attribute queries without an explicit window or trace default to the last 24 hours. Older records are not backfilled with inferred types; use **Any type** to include them.

Legacy StatsD accepts at most 1 MiB per item, 1,000 lines/expanded points and 4 MiB of estimated expanded label data per envelope. Counters retain packed source numbers and become non-monotonic delta sums. Distribution values become individual observations. Gauges expose the last sample through native scalar queries; SDK interval min/max/sum/count are retained in native summary fields, without pretending to reconstruct the original samples. Set metrics are reported as `statsd_set` in unsupported receipts and never stored as a fake gauge. Native metric arithmetic uses floating-point values. Cumulative OTLP input continues through the authenticated native OTLP endpoint; cumulative semantics are not invented for the Sentry increment protocol.

The Rust `priority_sdk_legacy_metrics_and_release_correlation` test runs the Node 8.47.0 metrics aggregator and checks native counter totals, gauge last values, distribution means, escaped labels and absent set series. A live unsupported-set receipt check additionally verifies zero stored metrics. The same Rust test sends six signal families from Node 11.8.0 and verifies exact release counts, native metric values, native record links, pagination, query bounds and write-only DSNs. Console acceptance covers release filtering, feedback navigation, onboarding and phone layout.

The native release API is `/api/projects/{project_id}/telemetry-releases`. It uses existing retained signal tables with exact release matching, stable pagination, example-record links, normal project permissions and a five-second query timeout. It creates no duplicate release store. First/last seen are observation times within the selected window, not deployment dates. Replay correlation follows associated errors and feedback rather than scanning recording blobs. Full release lifecycle management and release health are outside the SDK-ingestion contract.

For JavaScript 11.8.0, `dataCollection: { userInfo: false }` opts out of automatic user-data inference. Explicitly supplied user fields are a separate SDK choice. SDKs can still emit other unsupported items by default; disable unused features such as client reports where appropriate.

Native event queries accept `user_id`, or paired `tag_key` and `tag_value` parameters on `/api/projects/{project_id}/error-groups/{group_id}/events`. Both filters are exact string matches and remain subject to normal Temps project permissions. Filter values are limited to 1,024 bytes for user IDs/tag keys and 4,096 bytes for tag values. User and tag expression indexes support these queries. Arbitrary contexts remain queryable as native event JSON; they do not all become searchable columns.

Feedback has a separate ten-run acceptance matrix: Node 8.47.0, 10.17.0 and 11.8.0, current browser 11.8.0, and legacy browser 7.120.4, each over direct and tunnel transport. `scripts/sentry-feedback-conformance.py` runs the pinned official SDK generators, then verifies native report content, retry deduplication, error links, status changes, project isolation and deletion. Current browser runs also record the landing-page fixture and verify retained native replay snapshots and feedback/replay links. Correlated browser logs, spans and metrics exercise version-2 automatic IP/UA inference through native queries. The console workflow and landing-page playback are verified at desktop and phone viewport sizes.

The feedback inbox is under **Errors → Feedback**. Its native API is `/api/projects/{project_id}/feedback`, with read, triage and deletion routes under `/{feedback_id}`. These require normal Temps server authentication and project permissions; a public DSN can only submit reports. Report IDs are unique within project/source and authenticated DSN scope. Modern feedback retries use the SDK event ID; legacy reports use a stable content-derived identity because that format has no separate report ID. Feedback never creates error groups. Links resolve retained native records at query time, including records that arrive later. Deleting a report removes its content and contact information; future SDK resubmissions can recreate it.

Feedback accepts at most 100 reports, 128 KiB per report and 1 MiB total feedback payload per envelope. Messages are limited to 16 KiB and retained context to 64 KiB. It uses the existing DSN admission, body limits and shared telemetry concurrency permit, validates before writes, and inserts each batch in one transaction. Scope conflicts reject the batch, permanent failures roll back, and exact retries do not reset triage status. `x-temps-sentry-feedback-stored` and `x-temps-sentry-feedback-duplicates` distinguish new rows from retries. Native database tests cover concurrent retries, rollback and error links after retry-key cleanup.

Version-2 log, span and metric batches can request `infer_ip` and `infer_user_agent` with `auto` or `never`. Both default to `never`; absent/version-1 payloads do not infer. IP inference uses Temps' trusted-proxy resolution, and user-agent inference uses the shared native browser/OS parser. Explicit attributes take precedence. Inference adds attributes without changing DSN ownership or requiring a Temps browser SDK.

## Setup & Integration {{ anchor: true, id: 'setup' }}

Get started with error tracking in minutes using your existing Sentry SDK.

### Step 1: Get Your DSN

Each project gets a unique DSN (Data Source Name) for error reporting. The DSN format is:

```
https://<public_key>@<temps_app>/<project_id>
```

**Example DSN format:**
```
https://742ee692155dd1cb2cecd94838bb425d4b5a1184e5b57c0815e9d808a6f8d70d@your-temps-instance.com/1
```

### Get Your DSN

Visit your project's error tracking setup page to view and copy your unique DSN:

```
https://<temps_app>/projects/<project_slug>/errors?tab=setup
```

**Example:**
```
https://app.temps.davidviejo.dev/projects/my-app/errors?tab=setup
```

On this page, you'll find:
- **Your project's unique DSN** - Copy this to use in your Sentry SDK configuration
- Setup instructions for different platforms
- Environment-specific DSNs (if configured)
- Rate limits and configuration options

<Note>
**Important:** Each project has a unique DSN. You must copy your actual DSN from the setup page—the DSN shown in examples above is just a format reference. Your DSN will have a different public key.

**DSN Format:** The DSN consists of:
- **Public Key**: A 64-character hexadecimal string (unique per project)
- **Temps App URL**: Your Temps instance URL
- **Project ID**: Numeric project identifier

The DSN is automatically generated when you first visit the setup page.
</Note>

## Error Grouping {{ anchor: true, id: 'error-grouping' }}

Sentry SDK events use deterministic native fingerprints. Explicit fingerprint arrays override the default, and `{{ default }}` can be included as one component to refine it. An absent, empty, or single-default fingerprint uses the native default. These events do not use fuzzy matching: different explicit fingerprints stay separate even when messages are similar. Other native ingestion sources retain Temps similarity grouping.

### Grouping Strategies

<Properties>
  <Property name="Stack Trace Fingerprinting">
    Groups errors with identical stack traces (default)
  </Property>
  <Property name="Exception Type">
    Groups by exception class/type (TypeError, ReferenceError, etc.)
  </Property>
  <Property name="Error Message">
    Groups by error message pattern (parameterized)
  </Property>
  <Property name="AI Clustering">
    Native similarity grouping for other ingestion sources; excluded from Sentry fingerprint grouping
  </Property>
  <Property name="Custom Fingerprinting">
    Define grouping explicitly with an SDK fingerprint string array
  </Property>
</Properties>

### Custom Fingerprinting

Override default grouping with custom fingerprints:

<CodeGroup title="Custom Fingerprinting">
```typescript {{ title: 'JavaScript' }}
Sentry.captureException(error, {
  fingerprint: ['database-error', 'connection-timeout'],
});

// Dynamic fingerprint
Sentry.captureException(error, {
  fingerprint: ['api-error', String(error.response?.status ?? 'unknown')],
});
```

```python {{ title: 'Python' }}
with sentry_sdk.configure_scope() as scope:
    scope.fingerprint = ['database-error', 'connection-timeout']
    sentry_sdk.capture_exception(error)
```
</CodeGroup>

### Merge & Split Groups

Groups cannot be merged or split after the fact. To change how future events group, send a [custom fingerprint](#custom-fingerprinting) from your SDK: events with the same fingerprint land in one group, and events with different fingerprints are kept apart.

### Source Context (see the code) {{ anchor: true, id: 'source-context' }}

Temps can show the actual source code around each stack frame, not just
`file:line`. How the source gets there depends on the language:

- **JavaScript / TypeScript** — upload **source maps**. The original source
  travels inside the `.map` (`sourcesContent`), so minified production frames
  resolve to readable code automatically. The official Sentry build plugins and
  `sentry-cli` upload to Temps unchanged (Temps injects `SENTRY_URL` /
  `SENTRY_AUTH_TOKEN` for git-based deploys).

- **Go, Rust, Python, and other native languages** — these already report the
  *original* `file:line`, they just don't ship the source. Upload the raw
  source per release and Temps renders the code around each frame.

  Native source context is **opt-in per project** (Settings → General → *Error
  Tracking Source Context*) — application source is only stored when you enable
  it.

For **git-based deploys**, that's all you need: once the toggle is on, Temps
captures the source automatically after each deploy, keyed by the commit SHA.
By default it captures from the **Docker build context** — the exact directory
the image was built from — which is the right root for Dockerfile deploys and
monorepos (frame paths are relative to what was copied into the build). To
narrow or override it:

```yaml {{ title: '.temps.yaml' }}
sourceContext:
  root: services/api    # capture from here (relative to the repo); default: build context
  include: [go, rs]     # override the default source-extension set
```

...or set the **Source Root** in the project's error-tracking settings. For
**image deploys / external CI**, upload the source yourself (below).

The release you upload under **must match the SDK's reported release**
(`SENTRY_RELEASE`) — typically the deployed commit SHA or tag. For image-based
deploys Temps injects `SENTRY_RELEASE` from the deployed image tag/digest, so
key your upload the same way.

<CodeGroup title="Upload source in CI (native)">
```bash {{ title: 'Whole tree' }}
# Upload every source file under the repo, keyed by the release.
# file_path is each file's path relative to the root — exactly how a
# -trimpath Go binary (and most native SDKs) report frame filenames.
bunx @temps-sdk/cli errors source-files upload \
  --project-id 42 \
  --release "$CI_COMMIT_SHA" \
  --dir .
```

```bash {{ title: 'Single file' }}
bunx @temps-sdk/cli errors source-files upload \
  --project-id 42 \
  --release "$CI_COMMIT_SHA" \
  --file internal/gateway/middleware.go \
  --file-path internal/gateway/middleware.go
```

```bash {{ title: 'List / delete' }}
bunx @temps-sdk/cli errors source-files list   --project-id 42 --release "$CI_COMMIT_SHA"
bunx @temps-sdk/cli errors source-files delete --project-id 42 --release "$CI_COMMIT_SHA"
```
</CodeGroup>

<Note>
  **Compiled services (Go, Rust, …): don't hard-code the release.** Some SDKs
  let you set the release in code (e.g. `sentry.ClientOptions{ Release: version }`).
  If you bake a placeholder like `"dev"` into the binary, the SDK will **ignore**
  the `SENTRY_RELEASE` Temps injects at deploy time, and your events won't line up
  with the source you uploaded. Either:

  - leave the release **unset** in code so the injected `SENTRY_RELEASE` wins, or
  - bake the **real** commit/tag at build time, e.g. Go
    `-ldflags "-X main.version=$VERSION"` with
    `VERSION="${CI_COMMIT_TAG:-$CI_COMMIT_SHA}"` (and pass the same value as the
    `--release` you upload source under).
</Note>

## Error Resolution {{ anchor: true, id: 'resolution' }}

Manage error lifecycle from discovery to resolution.

### Error States

<Properties>
  <Property name="Unresolved">
    New or ongoing errors (default state)
  </Property>
  <Property name="Resolved">
    Marked as fixed (manually or automatically)
  </Property>
  <Property name="Ignored">
    Known errors that should be suppressed
  </Property>
  <Property name="Regressed">
    Error recurred after being resolved
  </Property>
</Properties>

### Mark as Resolved

<CodeGroup title="Resolve Errors">
```bash {{ title: 'CLI' }}
# Find the group ID (numeric) of an unresolved error
temps errors list --project-id 42 --status unresolved

# Resolve one error group
temps errors update --project-id 42 --group-id 123 --status resolved

# Reopen it
temps errors update --project-id 42 --group-id 123 --status unresolved
```

```typescript {{ title: 'API' }}
// Resolve error group 123 in project 42
await fetch('https://your-temps-instance.com/api/projects/42/error-groups/123', {
  method: 'PUT',
  headers: {
    'Authorization': `Bearer ${API_KEY}`,
    'Content-Type': 'application/json'
  },
  body: JSON.stringify({ status: 'resolved' })
});
```
</CodeGroup>

The CLI and API change one group at a time; to resolve several, run the command once per group ID.

### Auto-Resolution

Configure automatic resolution rules:

```yaml
# Auto-resolve errors
auto_resolution:
  # Resolve if no new events for X days
  no_events_for: 30

  # Resolve when new release is deployed
  on_release: true

  # Resolve when error rate drops below threshold
  rate_threshold:
    errors_per_hour: 1
    duration: 24h
```

### Ignore Errors

Suppress known errors you don't want to track:

<CodeGroup title="Ignore Errors">
```typescript {{ title: 'Client-Side' }}
Sentry.init({
  dsn: '...',
  ignoreErrors: [
    // Ignore specific error messages
    'ResizeObserver loop limit exceeded',
    'Non-Error promise rejection',

    // Ignore error patterns
    /^Loading chunk [\d]+ failed$/,
  ],

  // Ignore errors from specific URLs
  denyUrls: [
    /extensions\//i,
    /^chrome:\/\//i,
  ],

  beforeSend(event, hint) {
    // Custom ignore logic
    if (event.exception) {
      const error = hint.originalException;
      if (error.message?.includes('Network error')) {
        return null; // Don't send to Temps
      }
    }
    return event;
  }
});
```

```bash {{ title: 'CLI' }}
# Ignore one error group
temps errors update --project-id 42 --group-id 123 --status ignored
```
</CodeGroup>

Ignoring by message pattern is done in the SDK with `ignoreErrors`, as shown above; the server has no pattern rules.
